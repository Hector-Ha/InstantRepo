# InstantRepo Context

InstantRepo helps low-code users turn a repo URL or local folder into a prepared local repo. It must keep setup easy while making command risk and missing user action visible.

## Language

**Guarded Setup**:
Default flow where user reviews a setup plan and approves one setup step at a time.
_Avoid_: manual mode, safe mode

**Auto Setup**:
Opt-in batch flow that runs bounded setup steps after user accepts a danger modal.
_Avoid_: one-click install, blind auto-run

**Setup Plan**:
Ordered list of setup steps, attention items, env needs, services, and safety findings for one repo.
_Avoid_: checklist, script

**Setup Step**:
One actionable repo setup operation, such as preparing env, starting local services, or installing repo dependencies.
_Avoid_: task, command

**Attention**:
User-visible issue that needs awareness or action but is not itself command danger.
_Avoid_: risk, blocker

**Risk**:
Danger level of executing a command or touching local machine state.
_Avoid_: attention, warning

**System Tool**:
Machine-level tool outside the repo, such as Git, Node, Bun, Python, Go, Docker, Wails, winget, or brew.
_Avoid_: dependency, package

**Repo Dependency**:
Project dependency installed for the repo, such as Node packages, Python venv packages, or Go modules.
_Avoid_: system tool

**Install Script Policy**:
User choice for whether repo dependency install may run package lifecycle scripts.
_Avoid_: safer install commands

**Lifecycle Script**:
Package-manager script that runs during dependency install, such as `preinstall`, `install`, `postinstall`, or `prepare`.
_Avoid_: setup script

**Command Review**:
Classification path for commands that may be useful but need context before **Auto Setup** can run them.
_Avoid_: manual review

**Allowed Command List**:
User-editable policy list that lets known command patterns bypass repeated review.
_Avoid_: whitelist, safe list

**AI Advisor**:
Optional assistant that reviews shallow repo context and uncertain commands when deterministic checks are not confident.
_Avoid_: AI runner, source of truth

**AI Provider Key**:
User-provided credential for an external AI provider used by **AI Advisor**.
_Avoid_: built-in secret, repo key

**Service Credential**:
User-provided key, token, or secret for an external provider account needed by the repo.
_Avoid_: generated secret, fake key

**Generated Local Secret**:
Random development-only secret generated by InstantRepo for local auth, session, cookie, CSRF, or JWT needs.
_Avoid_: service key, production secret

**Dev Default**:
Conventional non-secret local development value used in an **Env Draft**.
_Avoid_: guessed secret, real credential

**Dev Default Allocator**:
Rule that chooses local ports, URLs, database names, and related **Dev Defaults** while avoiding conflicts inside the same **Env Draft**.
_Avoid_: hardcoded port guess, random URL

**App Topology**:
Detected local relationship between frontend apps, backend apps, databases, caches, and external services used to assign coherent **Dev Defaults**.
_Avoid_: same-name env linking, blind port sharing

**Port Conflict Action**:
User-approved action that helps free a local port needed by a **Dev Default** or setup command.
_Avoid_: silent process kill, random port reassignment

**Env Default Catalog**:
Versioned rule set that maps env var names and repo evidence to **Dev Defaults**, **Generated Local Secrets**, or **Service Credential** instructions.
_Avoid_: one-off env list, magic guesses

**Env Catalog Patch**:
App update that ships a newer **Env Default Catalog** with the InstantRepo desktop release.
_Avoid_: silent remote rule feed, editable JSON rules

**Vault Migration Rule**:
Catalog-provided mapping that updates **User Env Vault** metadata when provider env names or eligibility change.
_Avoid_: silent value rewrite, unsafe credential reuse

**Env Pattern Contribution**:
Opt-in report of env var names and public repo context from setup, used to improve future **Env Default Catalog** rules without collecting values.
_Avoid_: telemetry with secrets, source upload

**User Env Vault**:
User-managed secure store of reusable env values that InstantRepo can apply only when the **Env Default Catalog** allows it.
_Avoid_: catalog override, plaintext env library

**Vault Use Record**:
Local metadata showing which repo/env target used a **User Env Vault** value, when it was applied, and how often, without storing the value.
_Avoid_: secret log, telemetry

**Credential Validity Signal**:
Provider-specific evidence from redacted setup output that a **User Env Vault** value is invalid or needs user action.
_Avoid_: generic 401, raw secret log

**Provider Key Format**:
Provider-specific pattern used to recognize likely service credentials and catch obvious paste mistakes without proving validity.
_Avoid_: validation guarantee, secret type guess

**Credential Review Prompt**:
Neutral user prompt shown when a service credential might be duplicate, malformed, or otherwise questionable without claiming a specific cause.
_Avoid_: invalid-key error, duplicate-key error

**AI Env Review Bundle**:
Bounded env-specific context sent to **AI Advisor** for env default review without full repo contents or secret values.
_Avoid_: full repo upload, raw env dump

**Env Patch**:
Structured, validated change request for an **Env Draft** produced by deterministic rules or **AI Advisor**.
_Avoid_: raw file edit, AI-written .env

**Env Value Provenance**:
Metadata that records whether an env draft value came from an existing file, template, catalog rule, allocator, AI patch, vault, or user edit.
_Avoid_: guessing ownership from raw text

**Env File Role Classifier**:
Rule that classifies `.env*` files as local/dev targets, templates, or non-local targets from filename markers.
_Avoid_: user-chosen env file role, fixed allowlist only

**Env Target Inference**:
Rule that decides which folder should receive an Env Draft by inspecting env loaders, env usage, and runtime entrypoints.
_Avoid_: nearest manifest guess only, root-only .env

**Source Fix Suggestion**:
Suggested source change shown when env loading points outside safe repo boundaries or otherwise blocks local setup.
_Avoid_: source rewrite in env setup, outside-repo env write

**AI Review Log**:
Local diagnostic record of **AI Advisor** command decisions, kept outside the app UI.
_Avoid_: step history, user-facing activity

**Repo Diagnostic Export**:
User-triggered export of setup diagnostics for one installed repo.
_Avoid_: telemetry, cloud log

**Setup Session**:
One analyze flow and following setup actions for the same repo until app closes, repo changes, or user starts a new setup run.
_Avoid_: step run, app session

**Env Draft**:
Generated `.env` file content with preserved values, local defaults, placeholders, and instructions.
_Avoid_: secrets file, config dump

**Installed Repo**:
Tracked local repo with saved source URL, local path, lifecycle status, and setup step history.
_Avoid_: downloaded repo, clone

**Vault Manager**:
Dedicated app view where users manage **User Env Vault** entries, approvals, usage, and action-needed credentials.
_Avoid_: env editor clutter, clone-flow credential dialog

**Clone History**:
Local app metadata that records repo URLs, normalized URLs, clone paths, and installed repo state.
_Avoid_: registry, remote sync

**Local App Database**:
SQLite database owned by InstantRepo for local metadata, setup sessions, and status tracking.
_Avoid_: JSON tracker, server database

**Launch**:
User action that starts the prepared app after setup is complete.
_Avoid_: auto setup, run step

## Relationships

- A **Setup Plan** belongs to exactly one repo path.
- A **Setup Plan** contains zero or more **Setup Steps**.
- **Auto Setup** runs only bounded **Setup Steps** from the **Setup Plan**.
- **Auto Setup** stops before **Launch**.
- **Launch** uses the stored successful launch command when available, with refresh/re-analyze available separately.
- **Attention** may block **Auto Setup** even when **Risk** is low.
- A **System Tool** may be missing and create **Attention** without being a high **Risk** by itself.
- Installing a **System Tool** is outside **Auto Setup**.
- Default **Install Script Policy** favors compatibility by allowing normal install scripts.
- **Install Script Policy** is chosen in the **Auto Setup** danger modal because it changes compatibility versus caution.
- Alternate **Install Script Policy** can skip install scripts, but may break repo setup.
- Suspicious **Lifecycle Scripts** stop **Auto Setup** before dependency install and create visible **Risk**.
- **Command Review** uses deterministic rules first, then **AI Advisor** when enabled and needed.
- **AI Advisor** is optional and depends on a configured **AI Provider Key**.
- **AI Provider Key** is stored in the operating system credential store, not repo files or clone history.
- An **Env Draft** may include **Dev Defaults** and **Generated Local Secrets**.
- An **Env Draft** uses the **Env Default Catalog** to explain why each generated value or blank placeholder exists.
- Generated or intentionally blank values in an **Env Draft** have explainable reasons in the UI; saved `.env` comments stay sparse to avoid noisy large files.
- An **Env Draft** must not invent **Service Credentials**.
- InstantRepo ships **Env Default Catalog** changes through **Env Catalog Patches**.
- **Env Default Catalog** rules are data-only and may use only app-defined allowed actions; they cannot execute code, run commands, or bypass approval gates.
- Initial **Env Default Catalog** actions include preserving existing values, leaving blanks, generating local secrets, filling dev values, filling local service URLs, filling topology URLs, offering vault values, requiring user config, and showing **Attention**.
- New **Env Default Catalog** actions may be added later through app patches when app code explicitly supports them.
- The foundation does not support local **Env Default Catalog** overrides; users recover from bad suggestions by editing env values, changing vault approvals, or installing later app patches.
- A failed or unavailable app update never blocks **Env Draft** generation; InstantRepo uses the bundled **Env Default Catalog**.
- A **User Env Vault** may provide **Service Credential** values, but it cannot change the **Env Default Catalog** classification or make unsafe values higher authority than shipped rules.
- A **User Env Vault** value is applied to an **Env Draft** only after explicit user approval.
- **User Env Vault** approval is repo-scoped by default, with one-time use available for higher caution.
- Blank **Service Credential** variables may be filled from **User Env Vault** when a ready vault entry already has approval for the repo and env target.
- Existing non-empty env values are preserved and are not replaced by **User Env Vault** values automatically.
- **User Env Vault** stores values only in the operating system credential store.
- **User Env Vault** stores **Service Credentials** only, not **Generated Local Secrets** or **Dev Defaults**.
- **User Env Vault** eligibility is defined by the **Env Default Catalog** and can expand through **Env Catalog Patches**.
- **Env Catalog Patches** may include **Vault Migration Rules** for provider env name changes.
- **Vault Migration Rules** run as part of app update/startup migration.
- **Vault Migration Rules** update metadata only; credential values remain in the operating system credential store.
- Repo-scoped **User Env Vault** approvals survive high-confidence same-provider **Vault Migration Rules**; uncertain provider or purpose changes become action needed.
- If a **Vault Migration Rule** cannot safely map an existing entry, the entry becomes action needed until the user reviews it.
- OAuth client IDs and similar public provider identifiers are service configuration, not **User Env Vault** values by default, but should be grouped with related **Service Credentials** in setup guidance.
- User-specific provider configuration such as OAuth client IDs, Supabase URLs, and Firebase API keys stays blank with instructions rather than fake example values.
- **User Env Vault** supports multiple named values for the same provider or env var.
- **User Env Vault** stores a SHA-256 fingerprint for duplicate detection and shows only a short fingerprint fragment by default.
- Duplicate checks compare **Service Credentials** within the same provider, not across unrelated providers.
- **Provider Key Formats** may trigger a **Credential Review Prompt**, but they do not prove a credential is valid or invalid.
- **Provider Key Formats** live in app code or **Env Catalog Patches** and are not displayed as raw patterns in the UI.
- UI may show only generic masked examples for **Provider Key Formats**, such as `sk-...`.
- **Provider Key Format** changes from an **Env Catalog Patch** do not by themselves mark existing vault entries action needed or stop reuse.
- Saving a **Service Credential** with an existing provider-scoped fingerprint shows a **Credential Review Prompt** instead of silently creating another vault entry.
- **Local App Database** stores **User Env Vault** metadata and repo approvals only, never vault values.
- If the operating system credential store is unavailable, **User Env Vault** is unavailable instead of falling back to plaintext storage.
- **User Env Vault** values are masked by default in the Env Draft UI, with explicit reveal available.
- Revealing a **User Env Vault** value requires operating system authentication when available, otherwise an app confirmation prompt, and the reveal is temporary.
- Applying a **User Env Vault** value creates a **Vault Use Record** that identifies the repo, env target, variable name, and timestamp without recording the value.
- **Vault Use Records** remain until the user deletes the vault entry, repo record, or approval.
- **User Env Vault** entries may show validity hints inferred from redacted setup output, but InstantRepo must not store or display the underlying value.
- A **User Env Vault** entry marked invalid or action needed is not applied again until the user updates, confirms, or removes it.
- Invalid **User Env Vault** entries create **Attention** for affected env variables.
- **Credential Validity Signals** must be provider-specific and high-confidence before marking a **User Env Vault** entry invalid.
- Generic HTTP 401 or 403 output from a setup action that used a **User Env Vault** value creates action-needed **Attention** and suppresses reuse, but does not by itself prove the value is invalid.
- **Env Pattern Contribution** is offered as an install or onboarding checkbox and can be changed later in settings.
- **Env Pattern Contribution** is checked by default during install or onboarding, with clear wording and an easy opt-out.
- **Env Pattern Contribution** consent is shown once during install or first app setup, then managed later in settings.
- When enabled, **Env Pattern Contribution** sends env names and context after analysis, and value-free outcome metadata after **Save All**.
- **Env Pattern Contribution** sends env names and public repo context when available, never env values.
- **Env Pattern Contribution** deduplicates env names before sending.
- **Env Pattern Contribution** includes app and **Env Default Catalog** version metadata.
- **Env Pattern Contribution** includes operating system name and version, but no username or local path.
- **Env Pattern Contribution** includes detected stack and framework names.
- **Env Pattern Contribution** includes versions for recognized stack and framework packages when available, but not full dependency lists.
- **Env Pattern Contribution** includes relative env target paths, never absolute local paths.
- **Env Pattern Contribution** includes env classification and fill outcome metadata without values.
- **Env Pattern Contribution** save outcomes may include whether a generated value was edited, cleared, or saved, but never the final value.
- **Env Pattern Contribution** may include value-free save failure metadata such as relative target and error kind.
- **Env Pattern Contribution** may include AI involvement metadata such as review counts or whether an **Env Patch** was applied, without provider account or key details.
- **Env Pattern Contribution** does not include **User Env Vault** usage metadata.
- **Env Pattern Contribution** omits repo identity for private or local-only repos.
- With the default contribution setting, private or local-only repos do not contribute env names; users may separately enable private/local env-name contribution in settings.
- Public repo context is included only when the remote URL is confirmed reachable without authentication; SSH, authenticated, local-only, or uncertain repos are treated as private.
- Public repo context uses the normalized public repo URL after stripping credentials, query strings, and fragments.
- Public repo **Env Pattern Contribution** includes commit SHA when available.
- Public repo **Env Pattern Contribution** may include an env-relevant dirty working tree flag, but never local diffs.
- **Env Pattern Contribution** does not include branch names by default.
- **Env Pattern Contributions** inform future **Env Catalog Patches**, but do not directly change user-facing catalog rules without curation.
- **Env Pattern Contribution** does not collect provider key values or provider key formats.
- **Env Pattern Contributions** may be queued locally while offline and retried later.
- Offline **Env Pattern Contribution** queue is bounded to 100 payloads or 30 days and can be cleared in settings.
- Offline **Env Pattern Contribution** queue lives in the **Local App Database**.
- **Service Credentials** stay blank in an **Env Draft** with instructions for the user to obtain the real value.
- **Generated Local Secrets** are for local development and must be replaced by user-managed production secrets outside InstantRepo.
- **Generated Local Secrets** use 32 cryptographically random bytes encoded as unpadded base64url.

## Example Dialogue

> **Dev:** "Can **Auto Setup** install Docker if it is missing?"
> **Domain expert:** "No. Missing Docker is **Attention**. Installing Docker is a separate guided system action, not part of **Auto Setup**."

> **Dev:** "Can **Auto Setup** start the app?"
> **Domain expert:** "No. Setup prepares the repo. **Launch** is separate because app commands may run forever or need user choices."

> **Dev:** "Can AI make a command run during **Auto Setup**?"
> **Domain expert:** "Only through **Command Review**. If **AI Advisor** is high-confidence, setup can proceed with a visible note; low confidence asks the user."

> **Dev:** "Can an **Env Draft** fill `JWT_SECRET` and `SENDGRID_API_KEY`?"
> **Domain expert:** "`JWT_SECRET` can be a **Generated Local Secret** for dev. `SENDGRID_API_KEY` is a **Service Credential**, so leave it blank with setup instructions."

## Flagged Ambiguities

- "warning" was used for both **Attention** and **Risk**. Resolved: **Attention** means user must notice or act; **Risk** means command danger.
- "system tool" was unclear. Resolved: **System Tool** means machine-level tooling outside the repo, not project packages.
- "one-click auto-run" was too broad. Resolved: use **Auto Setup** for bounded setup batch, not blind execution.
- "safer install commands" was vague. Resolved: use **Install Script Policy**; default allows normal install scripts, advanced option can skip them with a breakage warning.
- Multi-command **Launch** is out of MVP. Current direction: support one primary launch command first; later consider user-defined launch groups that start multiple commands together.
- "secret" was used for both provider keys and local auth/session secrets. Resolved: **Service Credentials** stay blank; **Generated Local Secrets** may be generated for local development.
- Local database URLs were treated as requiring local service evidence. Current direction: local-first **Dev Defaults** are acceptable for developer setup, while managed service URLs remain user-editable.
- Managed datastore hints were ambiguous. Resolved: leave the env value blank, but include a local **Dev Default** suggestion in comments.
- Env defaults were treated as a fixed heuristic list. Resolved: maintain an incremental **Env Default Catalog** backed by framework/provider docs and observed repo patterns.
- User-provided env values were conflated with env classification. Resolved: **User Env Vault** can supply approved values, but classification authority stays with the shipped or signed **Env Default Catalog**.
- Catalog flexibility conflicted with desktop-app trust. Resolved: deliver catalog changes through **Env Catalog Patches** with bundled fallback instead of local editable rule files or silent remote rule feeds.
- Vault storage fallback was ambiguous. Resolved: use the operating system credential store only; no plaintext fallback.
- Plain text env editor conflicted with vault secrecy. Resolved: vault-backed values are masked in structured Env Draft UI, with local **Vault Use Records** for usage visibility.
- Credential failure detection was too broad. Resolved: provider-specific **Credential Validity Signals** mark values invalid; generic auth failures create action-needed **Attention** and stop reuse until the user acts.
- AI env editing needed bounded context and safe application. Resolved: use **AI Env Review Bundle** plus validated **Env Patch**; keep design open to future safer mechanisms.
